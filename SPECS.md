# SPECS — Blueprint Studio

> Technical specification for the product described in `PRD.md`. Clauses are the contract tickets cite.
> **ID scheme:** every rule has a verbatim ID `S<section>.<clause>`. Each clause ends with the PRD IDs it serves in brackets. IDs are stable; append, never renumber.

---

## S1 — System, configuration and models

- **S1.1** Three runtime parts: `web` (Next.js: UI and the CopilotKit runtime route), `agent` (FastAPI: AG-UI agent endpoint and REST API) and `db` (PostgreSQL 16). [NFR-9]
- **S1.2** `docker-compose.yml` starts all three with one command; configuration comes from one `.env` at the repository root; `.env.example` documents every variable with one worked OpenAI-compatible block and one Anthropic block. [NFR-9]
  > **Since the build:** S1.1 and S1.2 describe *server mode*. *Local mode* runs without Docker: `scripts/run_local.py` starts `agent` and `web`, and `DATABASE_URL=sqlite:///<path>` keeps sessions and checkpoints in a SQLite file in place of `db`. See README.md.
- **S1.3** Interview-model variables: `MODEL_PROVIDER` (`openai` for any OpenAI-compatible server, or `anthropic`), `MODEL_NAME`, `MODEL_BASE_URL` (optional), `MODEL_API_KEY` (optional for keyless local servers). Review-model variables, same meaning: `REVIEW_MODEL_PROVIDER`, `REVIEW_MODEL_NAME`, `REVIEW_MODEL_BASE_URL`, `REVIEW_MODEL_API_KEY`. Other variables: `DATABASE_URL`, `AGENT_URL` (how `web` reaches `agent`), `SESSION_TOKEN_BUDGET` (default `2000000`), `LANGSMITH_TRACING` (default `false`), `SKIP_MODEL_CHECK` (default `false`), `HOST` (default `0.0.0.0`), `PORT` (default `8000`). [NFR-4, NFR-8, NFR-10]
- **S1.4** The agent refuses to start, naming the variable, if `MODEL_PROVIDER`, `MODEL_NAME`, `REVIEW_MODEL_PROVIDER`, `REVIEW_MODEL_NAME` or `DATABASE_URL` is missing, if a provider value is unsupported, or if a numeric or boolean variable cannot be parsed. [NFR-10]
- **S1.5** Provider keys are read only by `agent`. The `web` build references no variable that holds a key. Settings objects never print key values. [NFR-6]
- **S1.6** One factory builds every chat model through LangChain's `init_chat_model`, for one of two roles: `interview` (from the `MODEL_*` variables) or `review` (from the `REVIEW_MODEL_*` variables). No other module imports a provider SDK or a provider-specific chat-model class. [NFR-10, D9]
  > **Since the build:** models are now reached through OpenAI's own SDK (`openai.AsyncOpenAI`, Chat Completions) instead of LangChain's `init_chat_model`. The rule stands: one module, `models.py`, builds the clients and is the only one that imports the SDK. See MODEL-CONNECTION.md.
- **S1.7** At startup the agent checks each role's model with one trivial tool call and one trivial structured-output call. If either fails, it refuses to start and names the role, the capability, the provider and the model. `SKIP_MODEL_CHECK=true` skips the check for offline tests. [NFR-10, US-52]
- **S1.8** The review model is *distinct* when its (provider, model name, base URL) triple differs from the interview model's. The result is computed once at startup and copied into each new session as `review_model_distinct`. [FR-14]

## S2 — Session state

- **S2.1** `DesignState` extends `copilotkit.CopilotKitState` and is the single source of truth for a session. [D3]
- **S2.2** Top-level fields: `session_id: str`, `stage: Stage`, `current_step: int` (1-5), `confirmed_steps: list[int]`, `design: Design`, `agent_design: Design | None` (the design as the interviewer last wrote it, S5.9), `critiques: list[Critique]`, `scorecard: Scorecard | None`, `gaps: list[Gap]`, `review_model_distinct: bool`, `prd_draft: PrdDoc | None` (the PRD currently awaiting sign-off or being extended), `prd_versions: list[PrdVersion]` (immutable snapshots, S7.4), `proposed_changes: list[ProposedChange]`, `seams: list[Seam]`, `tickets: list[Ticket]`, `tickets_approved_at: str | None` (ISO 8601 UTC), `id_counters: dict[str, int]`, `tokens_used: dict[str, int]` (keys `interview` and `review`), `token_budget: int`, `last_error: ErrorInfo | None`. [D3, D4]
- **S2.3** `Stage` is one of `interview`, `design_review`, `gap_resolution`, `prd_draft`, `prd_signoff`, `spec_synthesis`, `seam_gate`, `change_review`, `ticket_breakdown`, `ticket_gate`, `complete`. [D4]
- **S2.4** `Design` holds: `functional_requirements: list[Requirement]`, `non_functional_requirements: list[NfrTarget]`, `out_of_scope: list[Note]`, `capacity_estimates: list[Estimate]`, `entities: list[Entity]`, `relationships: list[Relationship]`, `endpoints: list[Endpoint]`, `storage_choices: list[StorageChoice]`, `components: list[Component]`, `flows: list[Flow]`, `cap_stance: CapStance | None`, `cache_policies: list[CachePolicy]`, `spofs: list[Spof]`, `failure_modes: list[FailureMode]`, `observability: list[Signal]`, `tradeoffs: list[Tradeoff]`, `extensions: list[Note]`. [FR-5]
- **S2.5** Every list item carries a stable `id` of the form `<prefix>-<n>`, issued by incrementing `id_counters[prefix]` and never reused within a session, even after deletion. Ticket IDs are zero-padded to two digits (`T-01`). [FR-6, G2]
- **S2.6** ID prefixes: `FR` requirement, `NFR` NFR target, `OOS` out-of-scope note, `EST` estimate, `ENT` entity, `REL` relationship, `EP` endpoint, `STO` storage choice, `CMP` component, `FLW` flow, `CACHE` cache policy, `FM` failure mode, `SPOF` SPOF, `OBS` signal, `TRD` trade-off, `EXT` extension, `GAP` gap, `F` feature, `US` user story, `CHG` proposed change, `SEAM` seam, `T` ticket. [S2.5, G2]
- **S2.7** Design item shapes. `Requirement`: `id`, `statement`. `Note`: `id`, `text`. `NfrTarget`: `id`, `category` (`latency`, `throughput`, `availability`, `durability`, `scale`, `security`, `cost`, `other`), `statement`, `metric?`, `target?: float`, `unit?`. `Estimate`: `id`, `quantity`, `formula`, `result: float`, `unit`. `Entity`: `id`, `name`, `fields: list[EntityField]`, `indexes: list[str]`, `est_record_bytes?: int`; `EntityField`: `name`, `type`, `key` (`pk`, `fk`, `none`), `references?` (entity ID, required when `key` is `fk`). `Relationship`: `id`, `from_entity`, `to_entity`, `cardinality` (`1:1`, `1:N`, `N:M`). `Endpoint`: `id`, `method`, `path`, `request`, `response`, `pagination?`, `errors: list[str]`, `rate_limit?`. `StorageChoice`: `id`, `data`, `technology`, `justification`, `rejected_alternatives: list[str]`, `status` (`proposed`, `decided`). `Component`: `id`, `name`, `kind` (`client`, `gateway`, `load_balancer`, `service`, `cache`, `queue`, `database`, `object_store`, `search`, `cdn`, `external`), `responsibility`. `Flow`: `id`, `name`, `kind` (`read`, `write`), `steps: list[FlowStep]`; `FlowStep`: `from_component`, `to_component`, `label`. `CapStance` (single value): `choice` (`CP`, `AP`, `mixed`), `rationale`. `CachePolicy`: `id`, `data`, `strategy` (`cache-aside`, `read-through`, `write-through`, `write-back`), `eviction` (`LRU`, `LFU`, `TTL-only`, `other`), `ttl_seconds?`. `FailureMode`: `id`, `scenario`, `behaviour`, `recovery?`. `Spof`: `id`, `component_id`, `risk`, `mitigation?`. `Signal`: `id`, `kind` (`log`, `metric`, `trace`, `alert`, `health-check`), `name`, `threshold?`. `Tradeoff`: `id`, `decision`, `gained`, `sacrificed`. All models forbid unknown fields. [FR-5]
- **S2.8** `Critique`: `step` (1-5), `strengths`, `bottlenecks`, `questions` (lists of strings). `Scorecard`: exactly five `DimensionScore` values, one per dimension (`communication`, `structure`, `judgment`, `depth`, `time`), each with `score` (1-4), `evidence: list[str]` and `advice`. [FR-9]
- **S2.9** `Gap`: `id`, `lens` (`security`, `efficiency`, `maintainability`), `item_ids: list[str]` (at least one existing design-item ID), `risk`, `decision_needed`, `severity` (`high`, `medium`, `low`), `status` (`open`, `resolved`, `accepted`), `note?` (the user's acceptance note), `resolved_by: list[str]` (design-item IDs recorded to resolve it), `feature_ids: list[str]` (set during PRD drafting, S7.2). [FR-12, FR-13]
- **S2.10** `PrdDoc`: signed-off sections `problem_statement`, `goals: list[str]`, `users: list[str]`, `features: list[Feature]`, `functional_requirements: list[PrdRequirement]`, `non_functional_requirements: list[PrdNfr]`, `scope: list[str]`, `out_of_scope: list[str]`, `open_gaps: list[Gap]`; and extension sections, empty until S8: `solution`, `user_stories: list[UserStory]`, `implementation_decisions: list[str]`, `testing_decisions: list[str]`, `further_notes: list[str]`. `Feature`: `id`, `name`, `description`, `requirement_ids` (at least one). `PrdRequirement`: `id`, `feature_id`, `statement`. `PrdNfr`: `id`, `category`, `statement`, `metric?`, `target?`, `unit?`. [FR-15, FR-16, FR-18]
- **S2.11** `UserStory`: `id`, `feature_id`, `actor`, `feature`, `benefit`, `acceptance_criteria: list[str]`, `requirement_ids` (at least one FR or NFR ID). [FR-18, G2]
- **S2.12** `PrdVersion`: `version` (`1.0`, `1.1`, `1.2`), `approved_at` (ISO 8601 UTC), `doc: PrdDoc`. Snapshots are never modified after they are appended. [FR-23, D7]
- **S2.13** `ProposedChange`: `id`, `section` (one of the signed-off section names in S2.10), `target_id?` (an FR, NFR or feature ID when the change targets one item), `kind` (`add`, `modify`, `remove`), `current_text?`, `proposed_text?`, `reason`, `decision` (`pending`, `approved`, `rejected`). [FR-19]
- **S2.14** `Seam`: `id`, `name`, `description`, `covers: list[str]`. `Ticket`: `id`, `title`, `what_to_build`, `blocked_by: list[str]`, `acceptance_criteria` (at least one), `story_ids` (at least one), `kind` (`slice`, `prefactor`, `expand`, `migrate`, `contract`). `ErrorInfo`: `code`, `message`, `retryable: bool`. [FR-20, FR-21, NFR-5]
- **S2.15** Every write from the frontend is validated against these schemas, including that IDs match their list's prefix, are not above the issued counter, are unique, and that cross-references (flow steps, SPOF components, relationships, foreign keys) point at existing items. An invalid write is rejected, the previous state is kept, and `last_error` names every violation. [FR-6, NFR-5]

## S3 — Session REST API

- **S3.1** `POST /api/sessions` with `{ "name": string }` creates a session (name 1-120 characters after trimming, else `422`) and returns `201` with `{ id, name, stage, current_step, created_at, updated_at }`. The new session's state has every S2.2 field, `stage` `interview`, step 1, and `token_budget` copied from `SESSION_TOKEN_BUDGET`. [FR-1]
- **S3.2** `GET /api/sessions` lists sessions by `updated_at` descending, with `limit` (default 20, max 100) and an opaque keyset `cursor` encoding (`updated_at`, `id`). [FR-1]
- **S3.3** `GET /api/sessions/{id}` returns the summary plus the state without `messages` and CopilotKit's internal field; `404` if unknown. [FR-1, NFR-3]
- **S3.4** `PATCH /api/sessions/{id}` renames, with S3.1's validation. [FR-1]
- **S3.5** `DELETE /api/sessions/{id}` removes the session row and all its checkpoints, returns `204`, and is idempotent. [FR-1]
- **S3.6** Every error body is `{ "error": { "code": string, "message": string } }`. [NFR-5]
- **S3.7** Every route declares typed request and response models, so FastAPI's OpenAPI 3.1 document at `/openapi.json` describes it completely, including the S3.6 shape for every non-2xx status. The frontend's REST types are generated from that document. [D14]

## S4 — Agent endpoint and runtime proxy

- **S4.1** The compiled graph is served at `POST /agent` by `add_langgraph_fastapi_endpoint` with a `LangGraphAGUIAgent` named `blueprint`. [D1]
- **S4.2** The graph uses an `AsyncPostgresSaver` checkpointer; the thread ID equals the session ID. [D10, NFR-3]
- **S4.3** `web` hosts `/api/copilotkit` with `CopilotRuntime` (`@copilotkit/runtime/v2`) whose `agents.blueprint` is an `HttpAgent` pointed at `${AGENT_URL}/agent`. [D2]
- **S4.4** The session page wraps its tree in `CopilotKit` with `runtimeUrl="/api/copilotkit"`, `agent="blueprint"` and the session ID as thread. [D2]

## S5 — Graph and interview

- **S5.1** Graph nodes: `interviewer`, `design_tools` (a tool-executing node that runs the interviewer's backend tool calls and returns to `interviewer`), `critic`, `review_security`, `review_efficiency`, `review_maintainability`, `gap_merger`, `prd_drafter`, `spec_synthesizer`, `seam_proposer`, `change_applier`, `ticket_planner`, `dag_validator`, `completer`. Routing is a pure function of state with no I/O; it may read `stage`, `current_step`, `confirmed_steps`, the number of critiques, `gaps`, `prd_draft`, `prd_versions`, `proposed_changes`, `tickets`, `last_error` and the newest messages. It ends the run when a frontend gate call is unanswered, when the interviewer has just replied in text, or when `last_error` is set. [D4]
- **S5.2** The interviewer's system prompt is assembled from the vendored files in `app-assets/` (S12): the interviewer instructions, then the course context, then the current stage and step, a compact ID-labelled summary of the design record, and any edit note (S5.9). [FR-2, FR-10]
- **S5.3** The interviewer records design data only through backend tools, one per `Design` list (`upsert_requirement`, `upsert_nfr`, `upsert_out_of_scope`, `upsert_estimate`, `upsert_entity`, `upsert_relationship`, `upsert_endpoint`, `upsert_storage_choice`, `decide_storage_choice`, `upsert_component`, `upsert_flow`, `set_cap_stance`, `upsert_cache_policy`, `upsert_failure_mode`, `upsert_spof`, `upsert_signal`, `upsert_tradeoff`, `upsert_extension`) plus `delete_item`. Tools validate against S2.7 and issue IDs per S2.5. In stage `gap_resolution` the tool `resolve_gap(gap_id, item_ids)` is also bound. [FR-5, FR-13]
- **S5.4** While `current_step` is 1, `upsert_component`, `upsert_flow`, `upsert_storage_choice` and `upsert_endpoint` are not bound to the model, so the scope-first rule is structural. [FR-2]
- **S5.5** Storage choices are created `proposed` and become `decided` only through `decide_storage_choice`, whose `basis` must name at least one of `read_write_ratio`, `consistency`, `latency`, `throughput`. The interviewer asks for a justification when it is missing. [FR-3]
- **S5.6** The interviewer requests step confirmation with the frontend tool `confirm_step(step, summary)`. Before the card opens, the graph checks blockers: Step 3 needs at least one failure mode; Step 4 needs at least one SPOF and every SPOF mitigated. If blocked, the call gets an error tool result listing the blockers and no card opens. [FR-4, FR-7]
- **S5.7** `confirm_step` answers `{ "approved": true }` or `{ "approved": false, "missing": string }`. Approval appends the step to `confirmed_steps` and advances `current_step`; rejection passes `missing` to the interviewer and stays on the step. [FR-7, D5]
- **S5.8** After each approved step the `critic` (interview model) stores one `Critique`. After Step 5 it stores the `Scorecard` and sets `stage` to `design_review`. [FR-9]
- **S5.9** Before each model call the interviewer compares `design` with `agent_design`; when they differ it adds a system note listing the user's edits by item ID. Every interviewer write sets `agent_design` to the design it wrote. [FR-6]

## S6 — Design review

- **S6.1** In stage `design_review` the three reviewer nodes run in parallel on the review model, each with structured output `list[GapFinding]` (`lens`, `item_ids`, `risk`, `decision_needed`, `severity`). Each receives the design record and the functional and non-functional requirements, not the transcript. [FR-11, G4]
- **S6.2** Reviewer checklists. Security: authentication and authorization for every endpoint; input validation; rate limits; secrets handling; sensitivity, retention and encryption of stored data; audit logging. Efficiency: pagination and indexes for every list read; caching against the read/write ratio; capacity estimates against storage choices; hot paths against latency NFRs; timeouts and retries on every flow hop. Maintainability: one clear responsibility per component; shared data stores between components; a single source of truth per rule; observability for every component; API versioning; ownership of every failure mode. [FR-11]
- **S6.3** Every reviewer prompt states: report gaps only; cite existing item IDs; never propose features, requirements, components or solutions; `decision_needed` is a question the user must answer, not an answer. Severity: `high` means it could cause a breach, data loss or an outage that breaks an NFR; `medium` means it degrades an NFR target or materially raises cost or maintenance; `low` is hygiene. [FR-12, G3]
- **S6.4** The `gap_merger` node (review model, structured output) merges the three lists: findings citing no existing item ID are dropped; findings on the same items with the same risk are combined, keeping the higher severity; survivors are issued `GAP` IDs with `status` `open`. Zero gaps sends the session to `prd_draft`; otherwise to `gap_resolution`. [FR-12]
- **S6.5** In `gap_resolution` the graph emits the frontend tool `decide_gaps(gaps)`, which answers a list of `{ "gap_id", "decision": "answer" | "accept", "text" }`. Accepted gaps get `status` `accepted` and `note`. Answered gaps are passed to the interviewer, which records design items and calls `resolve_gap`, setting `status` `resolved` and `resolved_by`. When no gap is `open`, `stage` becomes `prd_draft`. The review does not re-run. [FR-13]
- **S6.6** The workspace shows a persistent warning while `review_model_distinct` is false. [FR-14]

## S7 — PRD v1.0 and sign-off

- **S7.1** The `prd_drafter` (interview model, structured output) writes `problem_statement`, `goals`, `users`, `features`, `scope` and each open gap's `feature_ids`. Requirements are not rewritten: `functional_requirements` and `non_functional_requirements` are copied verbatim from the design record, each FR given the `feature_id` the model assigned, and `out_of_scope` is copied from the design's notes. `open_gaps` is every gap with `status` `accepted`. [FR-15]
- **S7.2** Validation, with one corrective retry: every FR in exactly one feature; every feature has at least one FR; every open gap has at least one `feature_id`; no unknown IDs. Failure after the retry sets `last_error`. [FR-16]
- **S7.3** In `prd_signoff` the graph emits `sign_off_prd(prd)`, answered `{ "approved": true }` or `{ "approved": false, "reason": string }`. Rejection re-runs `prd_drafter` with the reason. [FR-17]
- **S7.4** Approval appends `PrdVersion("1.0", now, prd_draft)` to `prd_versions` and sets `stage` to `spec_synthesis`. A version, once appended, is never changed. [FR-17, FR-23, D7]

## S8 — PRD v1.1 (`to-spec`), seams and proposed changes

- **S8.1** The `spec_synthesizer` (interview model) prompt contains `to-spec` verbatim from `app-assets/` with its attribution, the signed-off v1.0, the design record and the transcript, and the instruction to synthesize without asking questions. Structured output: `solution`, `user_stories`, `implementation_decisions`, `further_notes`, `proposed_changes`. It writes these into `prd_draft`, whose signed-off sections stay byte-identical to v1.0. Every open gap is appended to `further_notes` verbatim, prefixed by its ID. [FR-18, D8]
- **S8.2** Validation, with one corrective retry: every story has an existing `feature_id` and at least one existing FR or NFR ID; every FR is covered by at least one story; every proposed change names a signed-off section and, when present, an existing `target_id`. [FR-18, G2]
- **S8.3** The `seam_proposer` follows `to-spec` step 2 (the highest seams, as few as possible), stores `seams`, and emits `approve_seams(seams)`, answered `{ "approved": true, "seams": Seam[] }` (possibly edited) or `{ "approved": false, "feedback": string }`. Rejection re-proposes with the feedback. [FR-20]
  > **Since the build:** there is no `approve_seams` gate. The `seam_proposer` freezes PRD v1.1 with the seams it proposes and moves on (S8.4).
- **S8.4** Seam approval copies the seams into `testing_decisions` and appends `PrdVersion("1.1", now, prd_draft)`. If `proposed_changes` is empty, `stage` becomes `ticket_breakdown`; otherwise `change_review`. [FR-18, FR-23]
- **S8.5** In `change_review` the graph emits `review_changes(changes)`, answered with a decision per change ID. The `change_applier` (no model) applies approved changes to a copy of v1.1's signed-off sections, appends `PrdVersion("1.2", now, ...)` if at least one change was approved, and sets `stage` to `ticket_breakdown`. Rejected changes are dropped. [FR-19, FR-23]
  > **Since the build:** there is no `review_changes` gate. The `change_applier` accepts every pending change and freezes them as PRD v1.2; the PRD sign-off was the user's decision.
- **S8.6** The *current PRD* is the newest entry in `prd_versions`. Every later stage and every download reads the current PRD. [FR-23]

## S9 — Tickets (`to-tickets`)

- **S9.1** The `ticket_planner` (interview model) prompt contains `to-tickets` verbatim from `app-assets/` with its attribution and the current PRD *with `open_gaps` removed and gap entries removed from `further_notes`*, so open gaps cannot become tickets. Structured output: `list[Ticket]`. [FR-21, FR-22, G3]
- **S9.2** Validation, with one corrective retry: every ticket names existing stories; every story is covered by at least one ticket. [FR-21, G2]
- **S9.3** The `dag_validator` (no model) rejects unknown blockers, duplicate IDs and cycles, naming the cycle as an ordered ID list, and routes back to the planner with the error. Valid tickets are renumbered `T-01…` in topological order (ties by original order) with `blocked_by` rewritten, and the graph emits `review_tickets(tickets)`. [FR-22]
- **S9.4** `review_tickets` answers `{ "decision": "approve" }` or `{ "decision": "revise", "instructions": string }`. Revise re-runs the planner with the current tickets and instructions; approve sets `tickets_approved_at` and `stage` `complete`, and the `completer` posts one assistant message listing the downloads. [FR-22, FR-27]
  > **Since the build:** there is no `review_tickets` gate. A valid breakdown goes straight to the completer, which sets `tickets_approved_at` and `stage` `complete`.

## S10 — Downloads

- **S10.1** Each download is a pure function `render_<kind>(state, session_name) -> bytes`; none performs I/O or calls a model. [FR-29, D7]
- **S10.2** Kinds and file names: `prd-v1.0.docx` → `PRD v1.0.docx`; `prd-v1.1.docx` → `PRD v1.1.docx`; `prd-v1.2.docx` → `PRD v1.2.docx`; `requirements.docx` → `Requirements.docx`; `user-stories.docx` → `UserStories.docx`; `context.md` → `context.md`; `bundle.zip` → `<session name> - Blueprint.zip`. [FR-23 to FR-27]
- **S10.3** Availability: a PRD version kind once that version exists; the other kinds once `stage` is `complete`. `GET /api/sessions/{id}/downloads` returns every kind as `{ kind, available, reason }`; `GET /api/sessions/{id}/downloads/{kind}` returns the file, `404` for an unknown kind, `409` with the unmet condition for an unavailable one. The frontend never recomputes availability. [FR-23, FR-27]
- **S10.4** **PRD v1.x.docx**: title block (session name, version, approval date), then the PRD sections in this order: Problem Statement, Goals, Users and Stakeholders, Features, Functional Requirements (table: ID, Feature, Requirement), Non-Functional Requirements (table: ID, Category, Requirement, Metric, Target, Unit), Scope, Out of Scope, Open Gaps and Accepted Risks (table: ID, Lens, Severity, Affected items, Risk, Decision needed, Note); and for v1.1+: Solution, User Stories, Implementation Decisions, Testing Decisions, Further Notes. v1.2 adds a "Changes from v1.1" table listing each approved change. [FR-23]
- **S10.5** **Requirements.docx** (from the current PRD): FR table (ID, Feature, Requirement, Covering stories), NFR table (ID, Category, Requirement, Covering stories), and an appendix of open gaps and accepted risks. [FR-24]
- **S10.6** **UserStories.docx** (from the current PRD and tickets): stories grouped under feature headings, each with its sentence, acceptance criteria, requirement IDs and delivering tickets; then every ticket in ID order with what to build, blocking edges, delivered stories and acceptance criteria as a checklist; then a build-waves table (wave, tickets, blocked by). [FR-25]
- **S10.7** **context.md** is rendered from a fixed template in this order:
  1. *Role.* One paragraph: you are creating Jira issues for this project; this file is your only source.
  2. *Jira project.* `Site:` and `Project key:` lines left blank for the user; if either is blank when you start, ask for it.
  3. *Mapping table*, headed "Edit this table to match your Jira, then follow it exactly". Columns: Concept, Jira issue type, Parent, Links. Default rows: Feature → Epic, no parent, no links; User story → Story, parent the Epic of its feature; Ticket → Task, parent the Epic of its first story, links "relates to" each delivered story and "is blocked by" each blocking ticket.
  4. *Rules.* Create exactly one issue per listed ID and nothing else: no extra issues, sub-tasks, features, stories or tickets. Use each item's Summary line as the issue summary and its other fields as the description, formatted for Jira but not reworded. Create in order: features, then stories, then tickets in ID order, so parents and links exist when needed. Paste each open gap into the description of its feature's Epic under "Open gaps and accepted risks"; never create an issue for a gap. If an issue whose summary starts with a listed ID already exists, stop and ask before creating anything. ## S13 — Errors, retries, budget and observability

- **S13.1** Every model call retries on HTTP 429, 5xx and timeouts: up to 3 retries, exponential backoff from 1 s with full jitter, at least `Retry-After` when present. [NFR-5]
- **S13.2** A node writes state only after its model calls succeed. After exhausted retries it sets `last_error` (`code`, `message`, `retryable: true`) and changes nothing else. [NFR-5]
- **S13.3** Each response's token use is added to `tokens_used[role]`. Before any model call, if the sum of both roles reaches `token_budget`, the node does not call the model and sets `last_error` with code `budget_exhausted`. If a response carries no usage, the node estimates (prompt plus completion characters divided by 4, rounded up) and logs `usage_estimated: true`. [NFR-4]
- **S13.4** Structured-output calls request JSON-schema mode; if the provider rejects it, the call is retried once in tool-calling mode, and the working mode is cached per model for the process. [NFR-10, D6]
- **S13.5** Logs are one JSON object per line with `ts`, `level`, `session_id`, `node`, `event` and, for model calls, `role`, `latency_ms`, `input_tokens`, `output_tokens`; interviewer turns log `ttft_ms`; download requests log `export_ms`. Logs never contain keys, raw headers or full prompts. `LANGSMITH_TRACING=true` enables LangSmith tracing through LangChain's standard variables. [NFR-8, NFR-6, NFR-1, NFR-2]
